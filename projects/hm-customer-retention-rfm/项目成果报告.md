## 一、项目背景与定位

### 1.1 行业背景：快时尚的生死线是"留存"

时尚快消（fast fashion）行业近十年面临一个残酷的结构性矛盾：**获客成本持续攀升，但新客流失极快**。

- 拉新成本逐年上涨（流量红利消退），一个"买一次就消失"的新客，意味着获客预算的净亏损；
- 快时尚的复购天然依赖**上新节奏**（每周上新、换季清仓），错过上新触达窗口，客户很容易被竞品截胡；
- 因此，对 SHEIN、ZARA、H&M 这类品牌，真正的生死线不是"能拉来多少新客"，而是**"客户买过一次之后，还回不回来"**。

这构成了本项目的核心业务问题。它不是一道"要不要建个推荐模型"的技术题，而是一道**生意结构题**。

### 1.2 数据来源

- **来源**：Kaggle —— *H&M Personalized Fashion Recommendations* 竞赛官方数据（真实脱敏数据）
- **三张表**：

| 表 | 规模 | 关键字段 |
|---|---|---|
| `transactions`（交易明细） | 3179 万行，3.7GB | `t_dat`（日期）/ `customer_id` / `article_id` / `price` / `sales_channel_id` |
| `customers`（客户画像） | 137 万行 | `customer_id` / `age` / `club_member_status` / `fashion_news_frequency` 等 |
| `articles`（商品属性） | 10.5 万行 | `article_id` / `product_type_name` / `product_group_name` 等 25 个字段 |

- **数据窗口**：2018-09 至 2020-09，共 24 个月
- **数据口径**：价格为 H&M 内部标准化后的价格（以当地货币计），无订单号、无退货字段、无渠道细分

### 1.3 差异化定位（为什么这份数据值得做成"留存项目"）

这份数据在全网几乎只被用于**推荐系统竞赛**（预测"用户接下来会买什么"）。而本项目**刻意避开一切建模**，只做留存与分层分析。

> **"别人用它做推荐，我用它回答生意结构问题。"**

这一定位带来三重价值：
1. **差异化**：面试中能一句话讲清与网上千篇一律的推荐系统项目的区别；
2. **贴合岗位**：数据运营 / 用户增长 / 电商数据分析岗，面试官要的正是"留存 + 分层 + 复购"这套方法论；
3. **工程含金量**：3.7GB 大文件处理是真实生产级痛点，比在小数据集上跑模型更能证明工程能力。

## 四、技术路线与数据工程（本项目最硬的部分）

### 4.1 大文件分块处理（3.7GB 的核心解法）

3.7GB 的交易表、3179 万行，一次性 `pd.read_csv` 直接读入内存会导致**内存溢出**。采用业界标准的「**分块 + 聚合 + 二次聚合**」工程方案：

```
第 1 步  分块读取   pd.read_csv(chunksize=2_000_000, usecols=[4列])
第 2 步  逐块聚合   每块按「客户×月」聚合出 4 个指标
第 3 步  列表收集   结果 append 到 list，循环结束 pd.concat 一次拼
第 4 步  二次聚合   发现并合并「跨块重复」的同一客户×月
第 5 步  结果入库   to_sql 写入 SQLite，623 万行落盘
```

**细节说明：**

1. **分块读取**：按 200 万行/块切分，同时用 `usecols` **只保留分析所需的 4 列**（`t_dat` / `customer_id` / `article_id` / `price`），大幅压缩单块内存占用；
2. **逐块聚合**：每块内按「客户 × 月份」做命名聚合：
   ```python
   grouped = chunk.groupby(['customer_id', 'month']).agg(
       active_days=('t_dat', 'nunique'),   # 当月有交易的天数
       last_date=('t_dat', 'max'),         # 当月最后一次交易日期
       amount=('price', 'sum'),            # 当月总消费额
       items=('article_id', 'count')       # 当月购买件数
   ).reset_index()
   ```
   使用**命名聚合**（`agg(新列名=('原列', '函数'))`）而非老式 `agg({'列': ['函数']})`——前者列名直接、单层表头，规避了 MultiIndex 两层列名的后续重命名麻烦；
3. **列表收集 + concat**：分块结果先塞进 `list`，循环结束**一次性** `pd.concat`。刻意避免往 DataFrame 里逐块 append（pandas 的 append 每次都会复制整张表，是 O(n²) 的性能陷阱；官方已废弃 `DataFrame.append`）；
4. **二次聚合（关键防坑）**：`chunksize` 按行数硬切，**同一个「客户 × 月」可能被切开、散落在两个块中**。用 `monthly.duplicated(subset=['customer_id', 'month']).sum()` 验证出 **45.9 万个跨块重复**（`np.int64(459209)`），于是拼接后必须再做一次「客户 × 月」聚合把它们合并回一行：
   ```python
   monthly = monthly.groupby(['customer_id', 'month']).agg(
       active_days=('active_days', 'sum'),
       last_date=('last_date', 'max'),
       amount=('amount', 'sum'),
       items=('items', 'sum')
   ).reset_index()
   ```
   这里再次体现了**聚合粒度分层**的概念：第一轮是"明细 → 客户×月"，第二轮是"客户×月 → 客户×月（去重合并）"，两轮操作的对象和意义不同；
5. **结果入库**：`to_sql` 写入 SQLite 文件数据库 `hm.db`，623 万行「客户 × 月」宽表落盘。**文件库 vs 内存库**选择文件库：关 notebook 数据不丢，下次直接 `connect` 秒读，无需重跑 3.7GB。

**工程成果**：3179 万行明细 → 623 万行「客户 × 月」宽表，**压缩约 5 倍**，内存占用从"爆表"降到可稳定运行。

### 4.2 数据清洗：客户年龄

- **问题**：客户表 `age` 存在缺失值 + 极端异常值（100+ 岁）；
- **策略**：自定义函数 `clean_age`，将 `缺失 / <16 / >90` 的值**置为 `np.nan` 而非填充**：
  ```python
  def clean_age(a):
      if pd.isna(a):
          return np.nan
      elif a < 16 or a > 90:
          return np.nan
      else:
          return a

  age['age_clean'] = age['age'].apply(clean_age)
  ```
  为什么**置空而非填充**？因为年龄在本项目中只用于"分层对比"，不参与核心计算。强行填充（如填中位数）会**人为制造假象**、掩盖真实的年龄分布。置空 + 如实交代缺失率，比填个数字更诚实，也更好讲；
- **清洗结果**：缺失/异常占比 **1.16%**（量级合理，说明规则不过火）；
- **分箱**：`pd.cut` 按 `[15,25,35,45,55,90]` 切成 5 个年龄段（16-25 / 26-35 / 36-45 / 46-55 / 56+）。

### 4.3 品类维度的二次加工

`monthly_sales` 表在聚合时丢失了商品维度（没有 `article_id`）。为了做品类分析，**重新分块读取交易表**（这次只留 `article_id` + `price` 两列），聚合成 10.5 万商品的 `product_revenue` 表，再 JOIN `articles` 表补齐 `product_group_name` 品类。

> 这是"为分析维度追加数据"的典型工程操作——**同一份原始数据，按不同分析需求提取不同的字段组合**。第一个月聚合掉商品维度，第二遍按商品维度重新聚合，两遍合起来覆盖了全部分析需求。

## 五、五项核心分析

> 以下每项分析按「业务问题 → 分析方法 → 关键发现 → 业务解读」四层结构展开。

### 5.1 RFM 分层 —— 客户价值结构诊断

**业务问题**：136 万客户的价值分布是怎样的？谁是核心、谁在流失？

**分析方法**：

| 指标 | 计算逻辑 | 业务含义 |
|---|---|---|
| R（Recency） | `julianday('2020-09-30') - julianday(MAX(last_date))` | 距数据末日最后一次消费的天数，越小越活跃 |
| F（Frequency） | `SUM(active_days)` | 累计活跃天数，越大越常买 |
| M（Monetary） | `SUM(amount)` | 累计消费额，越大越值钱 |

三个维度**量纲完全不同**（天数 / 次数 / 金额），无法直接比较，因此用 `NTILE(5)` 各打 1-5 分：

- **R**：`NTILE(5) OVER (ORDER BY recency_days DESC)` —— R 越小越好，降序把"小的"沉到后面拿高分；
- **F / M**：`NTILE(5) OVER (ORDER BY ... ASC)` —— 越大越好，升序把"大的"沉到后面拿高分。

再用 `CASE WHEN` 组合三个分数，划分出 **8 类客群**（`CASE WHEN` 从上到下命中即止，最严格的"三维全高"放最前）：

```sql
CASE
    WHEN R_score>=4 AND F_score>=4 AND M_score>=4 THEN '重要价值客户'
    WHEN R_score>=4 AND M_score>=4 THEN '重要发展客户'
    WHEN F_score>=4 AND M_score>=4 THEN '重要保持客户'
    WHEN M_score>=4 THEN '重要挽留客户'
    WHEN R_score>=4 AND F_score>=4 THEN '一般价值客户'
    WHEN R_score>=4 THEN '一般发展客户'
    WHEN F_score>=4 THEN '一般保持客户'
    ELSE '流失客户'
END
```

**关键发现**（人数分布）：

| 客群 | 人数 | 占比 | 收入贡献 | 价值判断 |
|---|---|---|---|---|
| 流失客户 | 595,126 | 43.7% | ~8% | 人多钱少，放弃或低成本唤醒 |
| 重要价值客户 | 337,152 | 24.8% | **66%** | 核心基本盘，重点维护 |
| 一般发展客户 | 145,779 | 10.7% | ~4% | 最近买过，有转化潜力 |
| 重要保持客户 | 131,296 | 9.6% | ~16% | 高价值但最近没来，需唤醒 |
| 重要挽留客户 | 55,026 | 4.0% | ~4% | 花钱多但快流失 |
| 一般价值客户 | 40,543 | 3.0% | ~1% | 活跃但低消费 |
| 一般保持客户 | 35,921 | 2.6% | ~1% | 常买但价值低 |
| 重要发展客户 | 21,438 | 1.6% | ~0.4% | 高消费但频次不足 |

**可视化 —— 客户占比 vs 收入占比双柱图**：

![RFM 八类客群：客户占比 vs 收入占比](outputs/RFM分层图.png)

（左起两类的收入柱远高于客户柱——**"人少钱多"**；流失客户则是客户柱远高于收入柱——**"人多钱少"**。）

**业务解读**：

1. **客户价值极度两极分化**：25% 的重要价值客户贡献 **66%** 收入，44% 的流失客户只贡献 8%。这是典型的"少数客户撑起大盘"结构；
2. **重要保持客户（10% 人贡献 16% 收入）是最具性价比的唤醒对象**：他们过去常买、花得多，只是最近没来——相比拉新，唤醒这批人的 ROI 高得多；
3. **留存是生死线**：客户结构决定了这门生意经不起流失，任何降低首月流失的动作都是在保护那 66% 的核心收入。

### 5.2 同期群留存 —— 客户流失节奏诊断（门面图）

**业务问题**：新客流失有多快？什么时候流失？留存有没有规律？

**分析方法**：

1. **算首购月**：`MIN(month)` + `GROUP BY customer_id` 得到每个客户的首购月（`first_buy` 表）。利用 `month` 是 `'2018-09'` 这种"年-月"字符串、字典序即时间序的特性，直接 `MIN` 即可；
2. **算活跃人数**：`monthly_sales JOIN first_buy USING(customer_id)`，给每行贴上首购月，再按「cohort × 活跃月」分组 `COUNT(DISTINCT customer_id)`；
3. **算分母**：按 cohort 数首购人数（`cohort_size`）；
4. **算月份差与留存率**：
   - `month_n`：用 `substr` 切出年月、`CAST` 转数字，`(年差)×12 + (月差)` 得到距首购的月份数；
   - `retention_pct`：`ROUND(active_users * 100.0 / cohort_size, 2)`。**必须用 `100.0` 而非 `100`**——SQLite 整数除法会截断为整数（44 而不是 44.85）。

**关键发现**（2018-09 首购 cohort 留存曲线）：

| 首购月 | month_n | 活跃人数 | 留存率 |
|---|---|---|---|
| 2018-09 | 0 | 140,340 | 100.00% |
| 2018-09 | 1 | 61,551 | **43.86%** |
| 2018-09 | 2 | 59,793 | 42.61% |
| 2018-09 | 3 | 56,736 | 40.43% |
| … | … | … | 缓慢衰减 |
| 2018-09 | 24 | 34,096 | **24.30%** |

**可视化 —— 留存热力图（项目门面图）**：

![H&M 客户同期群留存率热力图](outputs/留存热力图.png)

（行 = 首购月，列 = 距首购月数，格内数字 = 留存率%。斜对角线全红 = 首购当月 100%；向右下角颜色变浅 = 留存衰减。图中保留了 2018-09 ~ 2020-06 共 15 个 cohort、前 12 个月的数据完整区域。）

**三个核心洞察：**

1. **首月断崖**：100% → 43.86%，**新客第 2 个月就走掉一大半**。这是最扎心的数字——意味着拉新进来的人，大部分不会买第二次。对应动作：**新客首单后 30 天内要建复购钩子**（首单优惠券 / 会员引导）；
2. **缓慢衰减但非归零**：从 44% 慢慢掉到 24%——不是掉到 0。说明留下的人里有相当一部分是"慢热但忠诚"的。腰部客户值得持续经营，别一刀切当流失；
3. **每年 3~6 月留存率明显回升**：以 2018-09 cohort 为例，month_n=6~9（2019 年 3~6 月）留存率从 36% 爬到 42.7% 又回落——**换季购物驱动的复购**。时尚快消的复购有强季节性，营销要踩准换季节点。

**额外洞察 —— 拉新质量在下降**：热力图上越靠下的 cohort（越晚首购），首月留存率越低——2018-09 首购的 43.9%，2020-02 首购的只剩 **11.8%**。提示后期拉新渠道/人群质量在系统性下滑，投放策略需要归因与调整。

### 5.3 复购结构 —— 生意的"老客依赖度"（项目核心问题）

**业务问题**：这门生意到底靠老客复购，还是靠不断拉新？

**分析方法**：以"**活跃月份数**"划分客群——仅 1 个活跃月的为**一次性购买客户**，≥2 个月的为**复购客户**。用窗口函数 `SUM(COUNT(*)) OVER ()` 在分组后拿到全表总数当分母，计算两类的人数占比与收入占比。

```sql
SELECT
    CASE WHEN active_months = 1 THEN '一次性购买' ELSE '复购客户' END AS cust_type,
    COUNT(*) AS customer_count,
    COUNT(*) * 100.0 / SUM(COUNT(*)) OVER () AS customer_pct,
    SUM(total_amount) AS total_revenue,
    SUM(total_amount) * 100.0 / SUM(SUM(total_amount)) OVER () AS revenue_pct
FROM (
    SELECT customer_id,
           COUNT(DISTINCT month) AS active_months,
           SUM(amount) AS total_amount
    FROM monthly_sales
    GROUP BY customer_id
)
GROUP BY cust_type
```

**关键发现**：

| 客群 | 人数 | 人数占比 | 收入 | 收入占比 |
|---|---|---|---|---|
| 一次性购买 | 491,559 | 36.1% | 50,983 | **5.8%** |
| 复购客户 | 870,722 | 63.9% | 833,663 | **94.2%** |

**业务解读**：

1. **64% 的复购客户贡献 94% 的收入**——这是项目最核心的结论，直接回答"靠老客还是靠拉新"：**靠老客**；
2. 36% 的一次性客户只贡献 5.8% 收入——**拉新拉来的人里，1/3 买一次就走**，基本是获客预算的浪费；
3. **对应动作**：① 拉新要更精准（渠道筛选、人群定向，别把钱花在"买一次就消失"的人身上）；② 运营重心放在"**首单 → 复购**"的转化上——把 36% 的一次性客户往 64% 里转化。这与 5.2 的"首月留存断崖"是**同一个结论的两个角度，互相印证**。

### 5.4 品类帕累托 —— 收入集中度诊断

**业务问题**：收入集中在哪些品类？头部品类有多强？

**分析方法**：

1. 重新分块读交易表 → `product_revenue`（每个商品的总收入）；
2. `product_revenue JOIN articles USING(article_id)` 补齐 `product_group_name` 品类，`GROUP BY` 品类聚合收入；
3. 用窗口函数 `SUM() OVER (ORDER BY revenue DESC)` 计算**累计收入占比**（`cum_pct`），验证帕累托法则。

**关键发现**：

| 累计品类数 | 覆盖品类比例 | 累计收入占比 |
|---|---|---|
| 前 3 类（上身 / 下身 / 全身服装） | 16%（3/19） | **79.04%** |
| 前 4 类（+泳装） | 21% | 85.56% |
| 前 5 类（+内衣） | 26% | 91.70% |

**可视化 —— 品类收入帕累托曲线**：

![品类收入帕累托分析](outputs/帕累托曲线.png)

（蓝色柱 = 各品类收入（降序），红色折线 = 累计收入占比。前 3 类柱体高高耸起、红线飙到 79%，随后迅速走平——尾部 12 个品类合计贡献不足 5%。）

**业务解读**：

1. **帕累托法则真实成立**：16% 的品类（3/19）贡献近 8 成收入。**服装是绝对主业**；
2. **资源聚焦**：选品、备货、营销预算都应押在服装三大类（上身 / 下身 / 全身）——这是"吃饭的碗"；
3. **第二梯队**：泳装 + 内衣合计贡献 12.7%，是值得培育的第二增长曲线；
4. **尾部 12 类不到 5%**：不是没有价值，但更可能是"**搭配购买**"的角色（买衣服顺手带双袜子），单独做营销不划算。

### 5.5 沉睡客群 —— 召回价值评估

**业务问题**：半年（180 天）没买的客户有多少？历史价值如何？值不值得召回？

**分析方法**：基于 RFM 的 `recency_days`，用 `CASE WHEN recency_days > 180` 划分沉睡（>180 天未购）与活跃/近期，统计两类的人数占比、人均历史价值（`AVG(monetary)`）、收入占比。

**关键发现**：

| 客群 | 人数 | 人数占比 | 收入占比 | 人均历史价值 |
|---|---|---|---|---|
| 沉睡（>180 天未购） | 633,602 | 46.5% | **17.8%** | 0.25（活跃的 1/4） |
| 活跃/近期 | 728,679 | 53.5% | 82.2% | 1.00 |

**业务解读**：

1. **沉睡客群规模大（46.5%），但历史价值低**——人均只有活跃客户的 1/4，总共只贡献 17.8% 收入；
2. **大规模召回不划算**：给 63 万沉睡客户群发短信 / 邮件做召回，ROI 极差；
3. **更聪明的做法是选择性召回**：只召回沉睡客中"**花钱多但最近没来**"的那批——即 RFM 分层里的"重要挽留客户"（约 5.5 万人），把召回预算花在刀刃上。这个结论与 RFM 分层互相印证，能串成一条线讲。

## 六、交叉印证与综合结论

五项分析不是孤立的，它们**互相印证，形成一条完整的业务叙事线**：

```
RFM 分层（44% 流失、25% 核心客户贡献 66% 收入）
    ↓ 印证
复购结构（64% 客户贡献 94% 收入）  ←── 生意靠老客
    ↓ 回答为什么
同期群留存（首月断崖 44%）         ←── 流失在首月就发生
    ↓ 给出动作
品类帕累托（前 3 类占 79%）         ←── 资源聚焦方向
    ↓ 收敛
沉睡客群（46.5% 人只贡献 18%）     ←── 召回要精准
```

**综合结论**：这是一门**典型的老客驱动型生意**——收入高度依赖占比不到三分之二的复购客户，而流失集中发生在首月。运营的优先级应该是：

> **首月复购转化 > 换季节点召回 > 高价值沉睡客唤醒 > 拉新渠道优化**

五个结论从不同角度都指向同一件事：**把资源投向"已买过一次的人"，而不是无差别拉新。**

## 八、技术亮点清单（面试可讲）

| 技术点 | 说明 | 面试价值 |
|---|---|---|
| **GB 级分块处理** | `chunksize` + `usecols` 列裁剪 + 列表收集 + `concat` + 二次聚合 | "我处理过 3.7GB / 3179 万行真实数据" |
| **二次聚合防坑** | 用 `duplicated()` 验证出 45.9 万跨块重复并合并 | 体现"发现问题 → 验证 → 修复"的完整闭环 |

| **数据仓库建设** | SQLite 落盘 + 文件库/内存库取舍 + 多表 JOIN | 数据工程基本功 |
| **浮点除法陷阱** | SQLite 整数除法截断，必须 `*100.0` | 实战踩坑经验 |

## 九、局限性与方法反思（主动交代）

> 面试中主动交代局限性，反而比藏着掖着更能建立信任。

1. **数据时效**：数据截止 2020-09，无法覆盖疫后消费行为变化，结论外推需谨慎；
2. **Recency 参照日偏差**：数据实际最后一笔交易约在 2020-08-20（`R_score=5` 的客户 `recency_days` 全部为 41~42 天），并非手册假定的 09-30。所有客户的 R 值因此被**系统性高估约 40 天**。本报告使用 09-30 作为参照日以保持口径一致，并在分析中注明该偏差；
3. **无退货字段**：复购率为"口径内复购"（以交易为准），未剔除退货影响，可能高估真实复购；
4. **无订单号**：F 值用"活跃天数"（`active_days`）近似"购买频次"——同一天多次购买被计为 1 天，可能存在轻微低估；
5. **渠道维度未展开**：`sales_channel_id`（线上 / 门店）未纳入本次分析，不同渠道的留存特征可能存在差异；
6. **市场差异**：欧洲市场客单价结构 ≠ 东南亚跨境市场，数字不可直接平移，但**留存分析方法论可复用**；
7. **价格标准化**：价格为 H&M 内部标准化价格（非真实销售额），M 值反映相对消费水平而非绝对金额。

### 10.2 追问应对

| 面试官追问 | 应对话术 |
|---|---|
| "怎么处理缺失值？" | 年龄异常值**置空而非填充**——因为只用于分层对比，填充会引入假象；置空后如实交代 1.16% 缺失率 |
| "留存率怎么定义的？" | 第 N 月活跃人数 ÷ 该 cohort 首购总人数，口径清晰；首购当月=100% |
| "为什么做二次聚合？" | chunksize 按行数硬切，同一客户×月可能跨块。我用 duplicated 验证出 45.9 万重复，合并后才得到干净的 623 万行表 |
| "RFM 怎么打分？" | NTILE(5) 分五分位；R 越小越好用 DESC，F/M 越大越好用 ASC，保证"分越高=越好" |
| "结论可能被什么干扰？" | 数据止于 2020-09、无退货字段、Recency 参照日偏差约 40 天——已主动交代 |
| "为什么不用机器学习？" | 这个问题更适合用可解释的聚合 + SQL 回答；且体现了"先搞清业务结构，再谈建模"的分析思路 |
